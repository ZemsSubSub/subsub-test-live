# Техническое решение

## Формат результата

Настоящий набор отдельных файлов, не один гигантский HTML:

```
subsub_front_prototype_14.07.26/
  instructions/          <- этот набор md-файлов (не трогать в процессе работы, только читать + обновлять progress)
  css/
    tokens.css           <- цвета/типографика как CSS-переменные, из main.css репозитория
    styles.css           <- обычные CSS-классы для layout/компонентов, которые реально используются
  icons/
    product_analytics.webp   <- реальные файлы иконок, скопированные из репозитория как есть
    product_live.webp
    ... (см. 04-content-reference.md за полным списком)
  js/
    nav.js               <- по минимуму: активное состояние сайдбара, разворот подменю Live, FAQ-аккордеон
  home.html
  live-overview.html
  live-streams.html
  ... (по одному файлу на страницу, по мере готовности)
```

Страницы — реальные отдельные `.html`-файлы, связанные обычными `<a href="live-streams.html">`, а НЕ один файл с JS-роутингом и `display:none/active` секциями. Это надёжнее, проще диффать и проще открыть/проверить один экран отдельно.

## Стилизация — без Tailwind CDN и без сборки

В прошлой сессии использовался `@tailwindcss/browser@4` через CDN прямо в HTML (`<script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4">` + `<style type="text/tailwindcss">@theme {...}</style>`). Технически в реальном браузере пользователя это работало (баннер с градиентом и т.п. отрисовывался), но:

- Требует интернет на CDN каждый раз при открытии файла.
- Невозможно нормально протестировать headless-браузером в текущей рабочей среде (падает с `performance.mark is not a function` в `jsdom`; в песочнице недоступен headless Chromium из-за отсутствующих системных библиотек и отсутствия sudo — см. `03-known-pitfalls.md`).

**Решение по умолчанию: обычный, руками написанный CSS**, без Tailwind вообще:
- `css/tokens.css` — переменные (`:root { --color-purple-900: #b351f6; ... }`) взятые 1:1 из `layers/core/assets/css/main.css` (блок `@theme`) — полный список в `04-content-reference.md`.
- `css/styles.css` — обычные классы под реальные блоки страниц (`.banner`, `.digital-products-grid`, `.card`, `.sidebar`, `.sidebar-item`, ...), без utility-классов уровня Tailwind. Так проще читать, дебажить и точно совпадает с тем, что реально нужно для этих конкретных экранов — не нужно тащить весь Tailwind ради десяти страниц.

Если позже понадобится точное соответствие Tailwind-классам из кода (например для будущей синхронизации с Figma/Storybook) — это отдельная будущая задача, не блокирует прототип.

## Иконки и картинки

Копировать реальные файлы из `layers/core/assets/images/*.webp` в `icons/` этой папки как обычные файлы (не base64, не отдельный `.js` с закодированными строками — в прошлый раз это запутало пользователя). Ссылаться обычным `<img src="icons/product_analytics.webp">`.

Полный список нужных файлов для сайдбара — в `04-content-reference.md`.

## JS — по минимуму, без шаблонов для статичного контента

**Не генерировать статичные карточки/списки/навигацию через JS `innerHTML`-шаблоны.** В прошлый раз именно так молча сломался весь прототип (см. `03-known-pitfalls.md`) — одна испорченная строка в JS-шаблоне обрушила всю страницу без видимой ошибки.

Вместо этого: писать HTML для карточек/пунктов навигации/таблиц напрямую, как обычную статичную разметку. JS оставить только для того, что реально интерактивно и не имеет смысла как статика:
- подсветка активного пункта сайдбара (можно и через `<a class="active">` вручную на каждой странице — тоже нормально, без JS);
- разворот подменю Live (Overview/Streams);
- аккордеон FAQ (можно через `<details>/<summary>` вообще без JS — так и было сделано в прошлый раз, это сработало нормально).

## Верификация перед показом пользователю

1. Открыть файл в настоящем браузере (можно попросить пользователя открыть у себя, либо — если появится доступ к Windows MCP/DevTools — через него).
2. Проверить консоль на ошибки.
3. Сверить визуально с https://app.subsub.io — сначала на глаз, при возможности — скриншот прода рядом со скриншотом файла.
4. Если в рабочей среде снова нет headless-браузера для автоматической проверки — не выдавать это за "проверено"; явно сказать пользователю, что визуальная проверка не была сделана автоматически, и попросить его сверить самостоятельно (как это в итоге и произошло в прошлой сессии — только там об этом сказали слишком поздно, после того как показали пользователю сломанный результат).
