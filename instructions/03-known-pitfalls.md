# Известные грабли (из предыдущей сессии) — чтобы не повторять

## Рабочая среда (sandbox / `mcp__workspace__bash`)

- **pnpm-симлинки в `subsub_platform_front` ломаются при монтировании Windows-папки в Linux-песочницу.** `node_modules/nuxt` и другие пакеты дают `Input/output error` при попытке прочитать через симлинк. Из-за этого **нельзя запустить `pnpm dev` / реальный Nuxt-сервер репозитория из песочницы**. Если нужно реально запускать Nuxt-приложение — это делает пользователь на своей Windows-машине, не Claude в песочнице.
- **Нет sudo/root в песочнице.** `npx playwright install --with-deps` и `sudo apt-get install libxdamage1` не работают. `npx playwright install chromium` скачивает бинарник, но `browserType.launch()` падает из-за отсутствующих системных библиотек — headless-браузер в этой песочнице поднять не получится без переустановки самой среды.
- **`jsdom`** как более лёгкая альтернатива браузеру частично работает (можно поймать JS-ошибки типа `SyntaxError`/`ReferenceError` в вашем собственном коде), но **валится на `@tailwindcss/browser` CDN-скрипте** (`performance.mark is not a function` — которого в jsdom нет). Если нужно тестировать через jsdom — сначала вырезать тестовую копию файла без Tailwind CDN / внешних скриптов, тестировать только свой JS.
- Устанавливать npm-пакеты — не в `outputs/` (там уже есть посторонний символический `node_modules`, конфликтует, `EPERM`/`unlink`), а в отдельной чистой директории (например `/tmp/что-то`).
- ESM (`import`) не подхватывает `NODE_PATH` — если нужно переиспользовать глобально установленный пакет, делать `ln -sfn <путь до пакета> ./node_modules` в рабочей директории скрипта, а не выставлять `NODE_PATH`.

## Claude in Chrome

- `computer` screenshot с `save_to_disk: true` **не сохраняет файл на диск в этой среде** — только показывает картинку в чате. Нельзя использовать для сборки прототипа из реальных скриншотов (был такой план — не сработал, инструмент явно сказал "Do not retry with save_to_disk").
- Сразу после `navigate` клик по координатам может не срабатывать (SPA не успела гидратироваться) — добавлять `wait` перед кликом, или использовать `find`/ref-клик, или `javascript_tool` для прямого взаимодействия с DOM.
- `javascript_tool`, возвращающий `element.outerHTML` целиком с продовой страницы, может быть заблокирован ("[BLOCKED: Cookie/query string data]"). Вытаскивать точечно нужные атрибуты/текст, не весь HTML целиком.
- Большие JSON-дампы через `javascript_tool` обрезаются (`[TRUNCATED]`) — делать запросы уже, по частям (например, по одному пункту меню за раз, а не все девять сразу).

## Архитектурные ошибки прошлой попытки (не повторять)

- **Один большой HTML-файл с рендером карточек/сайдбара через JS `innerHTML`-шаблоны** — сломался молча: пустой сайдбар, пустые карточки, без видимой ошибки в интерфейсе. Причина — скорее всего повреждённый JS template-literal при одном из точечных `Edit`-правок (следы: `SyntaxError: Unexpected end of input` при тестировании через jsdom, `Unexpected end of input` в районе строки с кнопкой "Learn More"). **Урок: не строить статичный контент через JS-шаблоны; писать HTML напрямую.** См. `02-tech-approach.md`.
- **Иконки сайдбара — угадал line-icons (SVG-контуры) вместо реальных цветных webp-картинок.** Пользователь сразу заметил несоответствие. Реальные файлы — `layers/core/assets/images/product_*.webp` и `space_admin.webp`. Всегда проверять через DevTools/JS, что на самом деле рисуется (`<svg>` или `<img>`), а не предполагать.
- **Активное состояние пункта навигации — не фон, а inset-тень слева** (`shadow: inset 3px 0 0 0 var(--color-purple-900)` через `:has(input:checked)` на радио-группе). Изначально сделал через закрашенный фон — визуально не совпадало.
- **Отдельный `.js`-файл с иконками рядом с HTML** — пользователь не смог его "открыть" (видимо ожидал папку с картинками, а получил файл с закодированным текстом). Если встраивать ресурсы — либо в один HTML-файл целиком (тогда явно предупреждать что это один файл, не открывать `.js` отдельно), либо (лучше, см. `02-tech-approach.md`) — обычные файлы изображений в подпапке.
- **Не показывать результат пользователю, пока не открыл сам файл в реальном браузере** (или хотя бы не сверил логически построчно) — из-за отсутствия headless-браузера в песочнице визуальная проверка была пропущена, и пользователь увидел сломанную версию раньше, чем я. Если авто-проверка недоступна — прямо сказать об этом, не выдавать несделанную проверку за сделанную.
